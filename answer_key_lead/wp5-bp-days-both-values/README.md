## 원문에서 확인한 규칙

혈압 측정일 후보는 유효한 수축기와 이완기의 날짜가 겹치는 날이에요. 그중 마지막 날을 고르고, 그날 수축기와 이완기의 최솟값을 각각 사용해요. 수축기 140 미만이면서 이완기 90 미만이면 조절됨이에요. [CMS165 v13 공식 원문](https://ecqi.healthit.gov/sites/default/files/ecqm/measures/CMS165v13.html)의 계산 정의와 안내를 확인했어요.

받아 둔 [CQL 원문](../../thinking/research/valueset-and-zero-1027/sources/v13-CMS165-v13-0-000-QDM-5-6.cql)의 줄은 다음과 같아요. 원문 줄 전체는 [verification.json](verification.json)의 `cql_evidence`에 있어요.

| 정의 | 파일의 줄 | 뜻 |
|---|---|---|
| Blood Pressure Days | 65~71 | 수축기 날짜와 이완기 날짜의 공통인 날이에요. |
| Most Recent Blood Pressure Day | 89~92 | 그중 마지막 날이에요. |
| Lowest Systolic / Diastolic Reading | 77~87 | 선택한 날의 두 성분 최솟값을 각각 사용해요. |
| Has Diastolic / Systolic | 50~54 | 90 미만·140 미만을 적용해요. |
| Numerator | 101~103 | 두 기준을 함께 만족해야 분자에 포함해요. |
| Qualifying readings | 105~119 | 단위·기간·입원과 응급실 제외를 먼저 적용해요. |
| Denominator | 47~48 | 이번 측정일 변경으로 분모 자격을 바꾸지 않아요. |

완전한 날이 하나도 없으면 후보 목록이 비고 마지막 날짜는 NULL이에요. 분자는 0이고 분모에는 남아요. 날짜·수축기·이완기를 모두 NULL로 표시하는 기대예요. 빈 목록에서 마지막 원소를 얻는 의미는 [HL7 CQL의 Last와 Indexer](https://cql.hl7.org/09-b-cqlreference.html#last)로도 확인했어요. CQL의 분자 식이 true가 아니라고 한 것이며 NULL을 false와 같다고 설명하지 않았어요.

## 바뀌는 여덟 사례

사례 수는 출처·사람·기준 시점 하나를 기준으로 세요. 같은 입력을 두 기준 시점에서 확인한 경우 두 사례예요. A와 A′도 검증 대상은 따로 세지만 독립 환자로 합산하지 않아요. 화면 바꿔 넣기 9행은 표시 계약 하나로 세고, 아래 DB 요약과 집계는 43사례에 더하지 않아요.

| 사례 | 기존 결과 | 새 결과: 날짜 · 수축기/이완기 · 분자 기여 · 이유 |
|---|---|---|
| M1-t04-sep30 | 2025-08-01 · 150/NULL · 0 · 마지막 날에 한쪽 값만 | 2025-02-01 · 104/81 · 1 · 조절됨 |
| M1-t04-dec31 | 2025-08-01 · 150/NULL · 0 · 마지막 날에 한쪽 값만 | 2025-02-01 · 104/81 · 1 · 조절됨 |
| M1-t04-dia-sep30 | 2025-08-01 · NULL/75 · 0 · 마지막 날에 한쪽 값만 | NULL · NULL/NULL · 0 · 혈압 없음 |
| M1-t04-dia-dec31 | 2025-08-01 · NULL/75 · 0 · 마지막 날에 한쪽 값만 | NULL · NULL/NULL · 0 · 혈압 없음 |
| M1-t08-unit-sep30 | 2025-08-01 · NULL/81 · 0 · 마지막 날에 한쪽 값만 | NULL · NULL/NULL · 0 · 혈압 없음 |
| M1-t08-unit-dec31 | 2025-08-01 · NULL/81 · 0 · 마지막 날에 한쪽 값만 | NULL · NULL/NULL · 0 · 혈압 없음 |

`t04`는 2/1의 104/81로 돌아가므로 두 기준 시점에서 분자가 각각 1 늘어요. `t04-dia`와 `t08-unit`은 완전한 날이 없어서 날짜·값·이유가 바뀌고 분자는 0을 유지해요. E01의 A·A′ p1은 12/1의 124/92를 사용하므로 계속 조절 안 됨이며, 이유는 이완기 90 이상이 돼요.

입력 날짜·값·파일과 줄, 기존 결과와 새 결과, 손으로 따진 과정은 [expected.json](expected.json)의 각 `cases`에 있어요. M1의 관련 사례 21개, E01의 사람별 12개, A′의 2개, B의 6개, OMOP의 1개, 화면의 1개를 담았어요. 새 입력 사례를 만들어 넣지 않았어요.

## 실제 DB의 지표 네 값은 같아요

제품 DB를 읽기 전용 연결(`read_only=True`)로 조회했어요. 전체 실행에는 요청한 4GB 메모리·스왑 0 제한을 적용했고, SELECT와 읽기 트랜잭션만 썼어요. 기존 분모 대상에 대해 완전한 날 중 마지막 날의 판정을 다시 조회했어요. 쓴 SQL과 결과, DB 파일의 크기·수정 시각 확인은 [verification.json](verification.json)의 `database`에 있어요.

| 출처 | 9월 말: 기존 → 새 | 연말: 기존 → 새 |
|---|---|---|
| A | 3/5 → 3/5 | 4/6 → 4/6 |
| A′ | 3/5 → 3/5 | 4/6 → 4/6 |
| B | 4/9 → 4/9 | 3/9 → 3/9 |

A·B의 네 조합은 모두 그대로예요. A′의 두 조합도 따로 확인했어요. 여섯 조합 모두 일별 혈압에 한쪽 값만 있는 날이 0건이고, 날짜·두 값·조절 여부·이유가 바뀐 사람도 0명이에요. DB 파일의 크기와 수정 시각도 같아요. 이 결과는 로컬 DB에 대한 확인이며 원격 상태를 확인한 결과는 아니에요.

## 그대로 두는 정의와 사례

[결정 0001](/home/junhyun/dev/projects/fhir-indicator-line/docs/decisions/0001-indicator-definition-d1-d7.md)의 D5 측정일 선택과 그에 따른 D6 판정만 이번 질문에 맞춰 해석했어요. D1 날짜 글자·측정 기간·환자별 기준 연도, D2 분모 자격, D3 코드·mm[Hg]·입원 및 응급실 제외·숫자 없는 성분 처리, D4 같은 날 성분별 최솟값, D7 학습용 제외 범위는 유지해요. 수축기 140 또는 이완기 90이면 조절 안 됨이라는 기준도 같아요.

A′ 손 사례의 8/20 부분값은 9/30과 12/1보다 이르므로 최종 결과가 같아요. 부분값 원천이 사라진다고 가정하지 않았어요. 성분별 일별 값에 부분값이 남는 것과 최종 측정일로 인정하는 것은 구분해요.

화면 시험 `tests/test_v1_report.py:166~167`은 최종 테이블에 109.51/NULL을 직접 넣어요. 기존 `controlled`와 날짜는 바꾸지 않으므로 임상 규칙의 새 결과를 증명하지 않아요. 같은 대역 입력이면 소수와 NULL을 그대로 보여야 한다는 기대는 유지했어요. 사람별 원천 이력이 갖춰져 있지 않아 이 입력의 임상 재계산 결과는 미확인이에요.

## 이유 이름은 제안이에요

△ 새 규칙의 정상 계산 결과에는 「마지막 날에 한쪽 값만」이 남지 않아요. 완전한 날이 있으면 그날의 기준값으로 판정하고, 없으면 **기존 「혈압 없음」을 유지**하는 안을 추천해요. 이때 의미는 「측정 기간 안에 수축기·이완기가 모두 있는 유효한 혈압 측정일이 없음」이에요. 부분값 원문 자체가 없다는 뜻은 아니에요.

CQL은 한국어 이유 이름을 정하지 않아요. 리드가 더 명확한 표시를 원하면 「유효한 혈압 측정일 없음」도 가능해요. [expected.json](expected.json)은 기존 이름 유지 제안으로 적었고, 이름의 최종 수용은 리드가 정해요. 화면에 직접 바꿔 넣은 기존 이유 문자열의 표시 계약은 별개예요.

## 확인한 범위와 못 본 것

기존 사례와 부분값 관련 코드를 다시 검색해 A′의 이전 부분값, 기존 기대 결과 생성기들의 부분값 판정, 스키마·공개용 이유 목록까지 확인했어요. 제품 E01과 작업실 정본의 입력·기대 결과도 해시로 비교해요. 제품 기준은 현재 로컬 HEAD `1bb454c4a7c9`이고, 요청서의 `fd10709`와 혈압 SQL 세 파일은 같아요. 관련 시험의 줄 번호가 옮겨진 점을 반영해 현재 줄을 인용했어요.

43사례 중 8사례가 바뀌고 35사례가 같아요. 저장소의 모든 시험을 실행하거나 모든 원천 자원을 전수 재판정한 결과는 아니에요. CQL 엔진 실행, CMS165 전체 적합성, 새 규칙이 반영된 제품 실행, 리드 검수는 미확인이에요. 제품 검사는 이 세션 범위 밖이라 실행하지 않았어요. CQL 이전 버전 페이지는 열리지 않아 공통 Last·Indexer 의미의 보조 확인에 현재 공식 문서를 썼어요.

[verification.json](verification.json)에 입력 해시·검색 범위·원문 줄·수기 과정·DB 조회를 남겼고, [SHA256SUMS](SHA256SUMS)로 결과 파일을 확인할 수 있어요. 제품·결정·기존 기대 결과 쓰기 0, push 0이에요.
