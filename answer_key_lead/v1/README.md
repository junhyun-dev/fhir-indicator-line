# 코드 묶음 v1과 조회 화면의 기대 결과 초안이에요

글: 만들기 · 의료 · 기대 결과 · Codex · 2026-10-27

상태는 **리드 검수 전**이에요. 이 묶음을 쓴 것으로 제품 구현이나 화면 검증이 끝난 것은 아니에요. 제품 코드와 DB는 수정하지 않았고, 기존 기대 결과를 다시 만들거나 고치지 않았어요. 결과 파일은 이 폴더 안에만 만들었어요.

## 숫자는 어떻게 유지했나요?

| 병원 | 기준 시점 | 분자/분모 | 저장된 rate | 화면 표시 |
|---|---|---|---|---|
| A | 2025-09-30 | 3/5 | 0.6 | 60.00% |
| A | 2025-12-31 | 4/6 | 0.6667 | 66.67% |
| B | 환자별 기준 연도의 9월 말 | 4/9 | 0.4444 | 44.44% |
| B | 환자별 기준 연도의 연말 | 3/9 | 0.3333 | 33.33% |

화면 비율은 저장된 `rate × 100`을 소수 둘째 자리까지 표시하는 초안이에요. 기대값 CSV의 수치는 바꾸지 않아요. A의 60%를 60.00%로 적은 것은 표시 자릿수만 고른 것이에요. 두 병원을 합친 비율은 만들지 않아요.

연말 A 6명·B 9명은 원래 행에서 읽었어요. 환자 번호는 병원별로 두 시점의 내부 사람 키를 합쳐 정렬한 순번으로 제안해요. 같은 실행 안에서는 시점이나 필터를 바꿔도 번호가 유지돼요. 원래 사람 키와 그 해시·앞부분은 화면용 값에 넣지 않아요. 이 검수 자료의 근거 경로나 규칙 설명도 브라우저 payload에 복사하지 않아요.

실패 사례는 기존 경우 2 그대로예요. B 연말의 `numerator` 한 셀만 3에서 4로 바꾸면 S04는 실패하고, S05에는 `B / dec31 / bp_summary / numerator / 기대 3 / 실제 4` 한 행이 보여야 해요. 빠진 행과 남는 행은 각각 0개예요. 이 사례는 rate를 바꾸지 않으므로 화면에서 4/9를 다시 계산해 rate를 고치지 않아요. 요약 차이에 임의의 환자 상세 링크도 붙이지 않아요.

## 이름과 해시는 어떻게 정했나요?

정의 ID는 `bp-control-learning`, 코드 목록 ID는 `essential-hypertension-learning`, 두 버전 이름은 `v1`로 제안해요. 공식 CMS 버전 이름으로 쓰지 않아요. 목록과 버전의 결합 ID는 `essential-hypertension-learning/v1`이에요. 코드 목록은 현재 seed에서 생성한 검토용 사본이고, 별도의 수기 정본이 아니에요. A′의 같은 SNOMED 매핑도 보존하며 독립 병원이나 여섯 번째 코드로 세지 않아요.

파일별 해시는 Git blob의 **원래 바이트 전체**로 계산해요. 기존 파일의 CRLF·LF, 마지막 줄 끝, 공백, CSV 행 순서를 바꾸지 않아요. `files` 배열만 POSIX 상대 경로 오름차순으로 정렬해요. 코드 목록은 `hospital, source_system, source_code, source_vocabulary_id` 순으로 정렬해요.

정의 manifest의 바이트는 `expected.candidate_manifest`만 Python `json.dumps(ensure_ascii=False, sort_keys=True, indent=2, allow_nan=False)`로 직렬화하고 LF 하나를 붙인 UTF-8이에요. BOM은 없고 자기 해시·검수 근거·실행 정보는 포함하지 않아요. 그 SHA256은 **`dc187bf7fa0fbdcfc8c6a244abbed6a7cdf0872a9e748fcf8ee137a159129577`**이에요. 이는 이 초안의 정확한 내용에 대한 기대 해시이며 제품에 manifest를 설치하거나 등록했다는 뜻은 아니에요. 파일 구성이나 ID·직렬화 제안이 검수에서 바뀌면 초안 해시도 다시 확인해야 해요.

화면용 출력에 더할 다섯 필드는 설계 05 그대로예요. `definition_id`, `definition_version`, `code_set_version`, `definition_manifest_sha256`에는 초안의 고정값이 있고, `run_id`는 **실제 같은 실행 manifest의 비어 있지 않은 ID**와 일치해야 해요. `run_id_binding.fixed_value: null`은 미래 실행 ID가 아직 없다는 뜻이며, 실제 화면의 NULL을 허용하지 않아요. DB 열이나 키는 바꾸지 않아요.

## 무엇이 모호하거나 아직 정해지지 않았나요?

1. **원래 기록 키의 표시가 충돌해요.** 요청서 19줄은 S03의 원래 기록 키를 요구하지만 설계 06의 40·75줄은 전체 행 키의 출력을 금지해요. 기존 독립 기대 결과에도 그 키가 없어요. 실제 키는 지어내지 않고 `미확인`으로 남겼으며, 화면 출력은 허용하지 않는 것으로 초안에 적었어요. 내부 연결 검증용 키를 별도로 준비할지는 리드 검수가 필요해요.
2. **상세 예시의 범위를 구분해요.** 완전한 표준 두 행은 독립 기대 결과에 이미 있는 B의 140/60 사례를 골랐어요. 수축기 140은 140 미만이 아니어서 비조절이에요. A의 124/92 비조절 행도 함께 적었지만, 그 사람의 표준 두 행이나 원천 키는 기존 독립 기대 파일에 없어서 새 사실처럼 고정하지 않았어요. 같은 날 성분별 최솟값·동률·부분값·연결 누락의 동작 조건은 담았고, 새 수치 fixture는 만들지 않았어요.
3. **ID 이름·해시 직렬화·번호 배정·일부 문구는 이번 초안의 선택이에요.** 설계 05의 40줄도 식별자 이름이 구현 계약이 아니라고 적고 있어요. 이 선택들을 리드가 검수해야 하며, OpenCodelists가 이 이름이나 직렬화를 규정한다는 뜻은 아니에요.
4. **화면정의서와 현재 검사 단계 수가 달라요.** 화면정의서의 기존 다섯 단계에 현재 `check.sh`의 dbt 빌드·품질 검사를 별도로 더해 여섯 단계로 적었어요. 필수 셀 사례 입력 확인은 실행 전 조건으로 구분했어요. 사다리 ④의 기대값 일치와 DQD 9개·미매핑 경고는 다른 결과로 보여 줘요.
5. **현재 실행의 상태는 아직 없어요.** 과거 index 행으로 새 실행을 통과 처리하지 않아요. 이번 index 행이 없으면 실행 이력 없음으로, DB·manifest·payload 연결이 확인되지 않으면 미확인으로 남겨요. dbt의 pass/warn/error/skipped를 사다리의 통과/실패와 섞지 않아요. 구체적인 새 실행 시각과 결과는 구현 뒤 같은 실행에서 읽어야 해요.

## 어떻게 확인하나요?

이 폴더에서 `sha256sum -c SHA256SUMS`로 두 JSON과 글의 해시를 확인해요. JSON의 모든 기대값에 근거가 있는지, 근거 줄이 존재하는지, 원본 해시가 맞는지, 후보 manifest 해시를 같은 규칙으로 재현할 수 있는지도 확인했어요. 네 요약값과 환자별 controlled 합계, A의 날짜별 기존 CSV와 병원별 CSV가 같은지도 비교했어요. S02·S03의 표시값에는 원래 환자 ID가 없어요.

제품 `check.sh`는 실행하지 않았어요. 이 요청은 제품·DB를 읽기만 하고 이 폴더 밖에 쓰지 않는 작업이며, 그 명령에는 dbt 빌드와 실행 이력 쓰기가 포함돼 있어요. 이번 확인은 기대 결과 자료의 일관성 확인이고, 구현된 화면의 통과 판정이나 리드의 독립 검수를 대신하지 않아요.

회고: 독립 기대 결과에 있는 값과 구현 뒤에만 확인할 수 있는 실행·원천 연결 정보를 구분하니, 없는 키나 시각을 지어내지 않고 초안을 준비할 수 있었어요.
