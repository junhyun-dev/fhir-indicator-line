# 설계 초안 05 · 코드 묶음과 지표 정의에 버전 붙이기

글: 만들기 · 의료 · Codex · 2026-10-27

**현재 상태: 10/27 저녁 사용자 결정으로 추천안 구현을 승인받았어요. 구현은 `REQ-medical-v1-build-1027` 범위이며 별도 가지에서 검증해요.** 아래의 ‘지금은 만들지 않음’·열린 질문·후보 문구는 작성 당시 초안의 기록이에요.

**초안 작성 당시: 리드 검수·사용자 선택 전이에요. 구현·기대 결과 작성·고정·계산 변경을 시작하지 않았어요.** D1~D7, 결정 0001~0013과 현재 고정 범위는 그대로예요. 여기서 v1은 기존 학습용 정의를 가리키며, 제품에 버전 필드가 이미 있다는 뜻은 아니에요.

현재 구현을 읽은 기준은 작업 가지 `work/fhir-line-05-dbt-quality@1b554be`예요.

## 1. 문제

같은 B 자료에서 진단 조건만 바꾼 연말 대상은 현재 9명, ICD-10만 2명, ICD-9만 7명, 조사한 계열 확대는 11명이었어요. A를 그대로 둔 이 비교에서 A 연말 대상은 6명이에요. 이 숫자는 [기존 sensitivity.tsv](/home/junhyun/personal/builds/medical-data-hands-on/thinking/research/code-set-facts-1027/sensitivity.tsv)의 조사 결과이며 새 기대값이 아니에요.

현재 `bp_summary`에는 어느 코드 묶음으로 계산했는지 없어요. `cdm_source.vocabulary_version`은 어휘 설명이고, 기준 시점과 Git 커밋도 코드 묶음 버전을 대신하지 않아요. 또한 현재 OMOP 매핑은 서로 다른 원천 코드를 같은 320128로 모으므로, 표준 개념 번호 하나만 기록하면 원천 코드의 선택 차이가 사라져요.

[공식 v13 공개 변경표](https://ecqi.healthit.gov/sites/default/files/ecqm/measures/CMS165v13-TRN.xlsx)는 ICD-9-CM 세 코드의 삭제를 확인해 줘요. 다만 [기존 공식 값 집합 대조](/home/junhyun/personal/builds/medical-data-hands-on/thinking/research/valueset-and-zero-1027/README.md:18)는 v13·v14 전체 구성원, I10·59621000의 해당 판 포함 여부를 확보하지 못했어요. 따라서 B 2명을 공식 CMS165의 새 기대 결과라고 부를 수 없어요. 방문·제외 조건 등도 공식 전체 구현과 달라요.

## 2. 목표와 하지 않는 것

목표는 숫자에서 정의 버전·코드 묶음·실행 입력으로 돌아갈 수 있게 하는 것이에요. 첫 구현 후보는 기존 A 연말 4/6, B 연말 3/9를 유지하며 버전 근거만 붙여요. 임상적으로 어느 코드를 포함할지는 별도 결정이에요.

공식 CMS165 전체 적합성, 계열 확대, KCD 매핑, 새 어휘 받기, E01 실행은 이번 후보에서 하지 않아요. 원천 진단을 지우거나 올바른 OMOP 매핑을 개념 0으로 바꿔 지표에서 제외하는 방법도 쓰지 않아요. **원천 코드의 임상 의미를 매핑하는 일과 특정 지표의 코드 집합에 포함하는 일은 달라요.**

## 3. 대안과 대가

| 대안 | 바뀌는 파일·출력 | 시험·기대 결과의 대가 | 판단 |
|---|---|---|---|

| C · CMS처럼 지표 이름에 버전 표시 | 지표 이름·도움말·설정에 버전을 적고 화면의 제목을 바꿔요. | 이름만 같고 실제 파일이 달라지는 경우를 별도로 막아야 해요. 기대 결과 파일도 이름만 바꿔서는 충분하지 않아요. | B에 더할 사람용 표기로는 좋아요. 이름만으로 입력을 고정하지 않아요. |
| D · DB의 fact·summary에 정의 버전을 넣어 동시 보관 | `fct_bp_person`·`bp_summary`와 JOIN 키·소비자·열 계약이 바뀌어요. | 여러 정의의 행이 섞이지 않는 키 시험과 버전별 기대값이 필요해요. 현재 frozen 범위를 바꾸는 별도 승인이 필요해요. | 여러 정의를 동시에 서비스할 때 다시 검토해요. 첫 구현에는 커요. |

OpenPrescribing의 고정 코드에서는 선택한 지표의 기존 값을 삭제한 뒤 재계산하고, 결과 키에 정의 버전을 따로 두지 않아요. 이 경로만 참고한 비교예요([import_measures.py:111](https://github.com/bennettoxford/openprescribing/blob/5a741b6f92c0d8f787d7b1345ade1e5de13a5b95/openprescribing/frontend/management/commands/import_measures.py#L111), [models.py:710](https://github.com/bennettoxford/openprescribing/blob/5a741b6f92c0d8f787d7b1345ade1e5de13a5b95/openprescribing/frontend/models.py#L710)).

OpenCodelists는 목록 ID와 버전 ID를 구분하며, 최신판 주소와 특정 버전 주소가 달라요. OpenSAFELY는 프로젝트의 목록 설정에서 버전을 지정하고 내려받은 파일·URL·날짜·해시를 별도 기록해요. 이 구조를 참고하는 것이지 서비스를 도입하거나 임상 적합성을 보증받는 것은 아니에요([공식 버전 설명](https://www.opencodelists.org/docs/#codelist-ids-and-versions), [프로젝트 입력 기록](https://docs.opensafely.org/codelist-project/#addingupdating-a-codelist-csv-file), 10/27 확인).

## 4. 추천과 구현 후보의 경계

**B에 C의 사람이 읽는 이름을 더하는 안을 추천해요. 먼저 v1의 근거를 고정하고, 포함 코드는 그대로 둬요.** 기존 `source_to_concept_map`과 `indicator_concepts`를 정본으로 유지하며 진단 코드를 또 손으로 관리하는 CSV를 만들지 않아요. 검토용 코드 목록을 내보내면 정본에서 생성한 사본이라고 표시해요.

버전 정보는 다음을 구분해요. 제안한 식별자 이름은 아직 구현 계약이 아니에요.

| 정보 | 뜻과 근거 |
|---|---|
| `definition_id`, `definition_version` | 학습용 지표와 D1~D7·병원별 적용 규칙의 버전이에요. 공식 CMS 버전과 같은 이름으로 쓰지 않아요. |
| `code_set_id`, `code_set_version` | 진단 코드 집합의 버전이에요. 원천 체계와 코드를 함께 다루고, 같은 문자열을 다른 체계의 코드로 대신하지 않아요. |
| 정의 manifest의 파일·SHA256 목록 | 매핑 seed·개념 seed·고정 계산 SQL·정의/결정 기록의 실제 바이트와 연결해요. 해시는 임상 의미의 옳고 그름을 판정하지 않아요. |
| 실행 manifest의 입력·커밋·dirty·정의 manifest 해시 | 어느 입력과 제품 상태로 실행했는지 기록해요. 어휘 판·코드 묶음 판·제품 커밋을 서로 대체하지 않아요. |

미래 후보 경로는 `config/indicator_definitions/<version>/manifest.json`과 `.local/.../runs/<run_id>/definition-context.json`이에요. **지금은 만들지 않아요.** 등록된 버전과 다른 파일 해시를 발견하면 옛 버전 이름으로 계산 완료를 표시하지 않아요. 의미가 같은 편집인지도 자동 추정하지 않고 검토해요. 이전 manifest를 고쳐 쓰지 않고 새 등록으로 남기는 안이에요.

기존 계산 층은 한 실행에서 정의 하나만 계산해요. 여러 버전을 한 DB에 억지로 합치지 않고 실행 산출물을 버전·run_id로 분리하는 안이에요. 미래 v2 계산은 v1의 DB·산출물을 덮어쓰지 않는 별도 실행 범위를 먼저 정해야 해요. 원래 source code·system·임상 매핑은 보존하고, 코드 집합의 지표별 포함 여부는 별도 의미로 다뤄야 해요. 계열 확대 때문에 모든 진단을 본태성 고혈압 320128로 매핑하지 않아요.

## 5. 바뀌는 데이터 모양

첫 추천안에서는 DB의 `bp_summary(hospital, as_of_label, denominator, numerator, rate)`와 `fct_bp_person`의 기존 열·키를 그대로 둬요. 화면용 내보내기 객체 `public_summary`에 `definition_id`, `definition_version`, `code_set_version`, `definition_manifest_sha256`, `run_id`를 추가하는 안이에요. 예를 들어 A 연말의 값은 기존 6·4·0.6667을 그대로 읽고 그 옆에 정의 정보를 연결해요. B 연말도 9·3·0.3333 그대로예요.

따라서 **출력에 메타데이터를 더하는 변화는 있지만 DB 테이블 열을 더하는 변화는 없어요.** `bp_summary` 자체에 열을 넣자는 선택이면 대안 D가 되며, `models/reports`의 frozen 보호·기존 열 계약과 충돌하므로 별도 승인이 필요해요. OMOP 공식 표에 지표 버전 열을 넣지는 않아요(0004·0005).

## 6. 시험과 기대 결과

| 범위 | 기대값을 두는 방법과 완료 조건 |
|---|---|
| v1 | 기존 `expected/`·`expected_a_prime/`를 읽기만 해요. A 3/5→4/6, B 4/9→3/9와 A′의 기존 비교를 유지하고, 메타데이터를 뺀 내보내기 행이 기존 행과 같은지 확인해요. |
| v2 후보 · 공식 코드 변경에 맞추는 방향 | 기존 조사에서 B의 ICD-10 제한은 2명이었지만 공식 전체 결과는 아니에요. 값 집합·제외 규칙·병원 B 적용 범위를 확인하기 전에는 공식 v13 기대값으로 고정하지 않아요. |
| v2 후보 · 계열을 넓히는 방향 | 기존 관측 코드의 접두 범위 확대는 B 11명이었어요. 이 수는 민감도 조사이며 추가 코드의 임상 의미·표준 개념 대응·지표 이름을 따로 정해야 해요. 분자와 비율도 새 독립 계산이 필요해요. |
| 새 기대값 작성 | v1 파일을 고치지 않아요. 예컨대 `expected_versions/<definition>/<version>/` 같은 별도 위치를 다음 요청에서 지정하고, 구현 담당과 다른 세션의 초안→리드 검수→해시·읽기 전용 고정 뒤 구현해요. 이번 작성자가 새 기대값을 쓰지 않아요. |
| 실패 반례 | 코드/체계가 다른데 같은 문자열, 같은 버전 이름에 다른 해시, v1 행에 v2 표기, 버전이 다른 요약의 혼합, 검토 전 v2를 완료로 표시하는 경우를 거부해야 해요. |

코드를 실제로 바꾸는 v2는 매핑과 포함 정책을 분리한 새 설계·기대값이 필요해요. 고정 계산·개념 seed를 바꿔야 한다면 리드가 기존 결정을 대체하는 범위를 명시하고 사용자 승인 뒤 진행해요. 이번 초안이 그 권한을 주지 않아요.

## 8. 열린 질문 — 사용자가 정할 것

1. **현재 포함 코드는 유지하고 버전 근거부터 붙일까요?** 추천은 예예요. v2 정책 변경은 분리해요.
2. **버전 정보는 먼저 화면용 출력에만 붙일까요, DB fact·summary까지 바꿀까요?** 추천은 화면용 출력부터예요. DB를 바꾸면 고정 범위·키·기대값의 새 승인이 필요해요.
3. **다음 임상 정의 변경은 공식 코드 집합 근거를 확보한 뒤 정합성을 높이는 방향과, 계열 확대를 별도 지표로 연구하는 방향 중 무엇을 먼저 볼까요?** 둘의 미확인 사실을 사용자에게 추측하게 하지 않고 담당이 먼저 확인해요. 현재 추천은 v1을 유지하는 것이에요.

리드가 검수한 뒤 선택 자료로 사용할 초안이에요. 결정 기록 0001~0013과 기존 설계 04는 그대로 두었고, 현재 미확인과 E01 보류를 이 초안으로 해제하지 않아요.
